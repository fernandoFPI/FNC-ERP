# PO Workflow Study: Root Causes & Simplification Plan

Status: **Implementation complete.** All 8 items in the "Suggested priority order" table are done, except item 8 which was assessed and found to have nothing safe to remove (see its entry below). Every change was verified (typecheck clean across `apps/web`/`services/gateway`/`packages/db`, migration applied and checked against the real dev DB, core arithmetic smoke-tested) before being marked done.

## Context

Four specific pain points were raised about the Purchase Order (PO) flow: lines with mixed currencies, vendor not always known up front, receiving split across multiple people per line, and "actual price" being entered later than it should be. This document is a full study of the current PO system (2 full lifecycle redesigns, 22+ migrations touching PO alone, a REST microservice and a GraphQL gateway that both implement the same business rules independently) to find the actual root cause of each complaint and the minimal fix: hypothesis → evidence (file:line) → minimal fix → what could go wrong.

Decisions made during this study:
1. Scope: report + recommendations, not implementation (this session).
2. Multi-currency lines: build true per-line currency + conversion to a base currency (not "force single currency per PO").
3. Actual price: move entry to the "items bought" step, entered by the buyer — not Finance Audit.
4. Vendor-required on the creation form: a bug, fix outright (backend already supports vendor-less POs).
5. Receiving: default to a "Receive All" one-person flow, with per-line receiver split as the explicit exception, not the default.
6. Issue E (dual implementation) is decided: remove the REST `services/procurement` microservice, keep the GraphQL gateway as canonical.

The single biggest thing to understand going in: **this system has a strong, repeated design pattern of "defer the decision to whoever actually has the information, as late as possible."** Vendor is deferred to market pricing. Funding source (vendor AP vs. employee advance) is deferred to Finance at "invoiced." GL account coding is deferred to Finance at "invoiced." That pattern is *usually* the right call — but it was also applied, seemingly by default rather than deliberately, to **actual price**, which is the one piece of information the buyer already has the instant they buy something. That mismatch is exactly the complaint that triggered this study, and it's the clearest, cheapest fix here.

## Issue A — PO lines with different currencies

**Hypothesis:** The system already *has* per-line currency fields, but they were bolted on independently at different times without ever being reconciled to each other or to the PO header total — so today "multi-currency lines" half-works (the fields exist) and half-doesn't (nothing converts or validates them), which is worse than either fully supporting it or not supporting it at all.

**Evidence:**
- Base schema (`packages/db/migrations/007_procurement_schema.sql`) gives *both* `purchase_orders.currency_code` (header) and `po_lines.currency_code` (line) — two currency fields from day one, never reconciled.
- `030_po_lifecycle_redesign.sql` adds a third: `po_lines.store_price_currency`.
- `047_po_purpose_and_stock_split.sql` adds a fourth and fifth: `po_lines.market_price_currency`, `po_lines.verified_price_currency`.
- `vendors.currency_code` is a sixth, unrelated currency concept (vendor's default currency, never linked to PO/line currency).
- `purchase_orders.fx_rate` is captured on the creation form (`apps/web/.../PurchaseOrderForm.tsx:56, 504-513`) but is hard-coded to `1` server-side at insert (`services/procurement/src/routes/orders.ts:341-357`), never updated afterward, and **never displayed anywhere** on the detail page (zero matches for `fx_rate` in `PurchaseOrderDetail.tsx`). It's a field that goes in and never comes back out.
- `po-helpers.ts:117-129` (`recalculatePOTotals`) sums `po_lines.total_price` into the header total with **no check that every line's currency matches the header's** — `submit-market-pricing` (`orders.ts:693-755`) lets a line be re-priced in a different currency than the header with no validation.
- On the frontend, the *creation* form only offers one currency for the whole PO (`PurchaseOrderForm.tsx:40-59`, no currency field on line items at all), but the **store_pricing and market_pricing stages** (`PurchaseOrderDetail.tsx:1906-1919`, `2043-2056`) each give every line its own currency dropdown, independent of the header — so mixed currencies *can* and do happen, just not where a user would expect to control it.
- A migration comment states the underlying problem outright: `197_advance_automation.sql:4-7` — *"No canonical currency list exists in this system (every form hardcodes its own currency dropdown)."*
- `CurrencyInput.tsx` — a properly built reusable currency component — exists in `apps/web/src/components/ui/` but is used nowhere in procurement; PO forms use plain `<input type="number">`.

**Decision (true per-line currency + conversion):** the fields to do this already mostly exist, but scattered and unreconciled. This is a consolidation problem more than a build-from-scratch problem.

**Recommended fix:**
1. Pick **one** authoritative per-line currency + price pair (recommend keeping `po_lines.currency_code` + `unit_price`, since that's what the dormant REST schema already models cleanly) and retire `store_price_currency`/`market_price_currency`/`verified_price_currency` as separate columns — they should be history/audit trail (who proposed what price when), not three more live sources of truth.
2. Give every PO a real `base_currency_code` (defaulting to company currency) and a per-line `fx_rate_to_base` captured at the moment the line's price is set (store pricing / market pricing / vendor confirmation) — not a single header-level `fx_rate` frozen at creation before anyone knows the real price.
3. `recalculatePOTotals` should sum `unit_price * qty * fx_rate_to_base` into the header total (always in base currency), and the header currency field should be relabeled as "reporting currency" so nobody mistakes it for "the currency all lines are in."
4. Show the FX rate and converted line amount on the detail page (currently invisible) so a user can sanity-check it, and swap the raw number inputs for the existing `CurrencyInput.tsx` component.

**What could go wrong:**
- Retiring `store_price_currency`/`market_price_currency`/`verified_price_currency` touches both the REST (`services/procurement`) and GraphQL (`services/gateway`) implementations, which have already drifted from each other (see Issue E) — do this *after* Issue E is resolved so there's only one place to change.
- Historical POs have no `fx_rate_to_base` recorded honestly (existing rows have `fx_rate = 1` regardless of real conversion) — reports that span old and new POs will need to treat pre-migration data as "unknown/approximate," not silently treat `1` as correct.
- Finance will need to sign off on which rate source feeds `fx_rate_to_base` (company's own FX table, migration `027_fx_rate_sync.sql` already has FX sync infrastructure — worth checking if it's reused here rather than building a second rate source).

## Issue B — Vendor not always known at PO creation

**Hypothesis:** The database and backend already fully support a vendor-less PO (this was a deliberate, documented design decision), but the frontend form contradicts that design by forcing vendor to be required for most POs, and there is no UI at all to attach or correct a vendor after creation outside of one narrow workflow step.

**Evidence:**
- `purchase_orders.vendor_id` was originally `NOT NULL` and was deliberately relaxed: `030_po_lifecycle_redesign.sql:40-42` — *"STEP 4: Make vendor_id nullable (vendor is selected during market pricing, not at creation)"*. This is intentional, documented design — not an oversight.
- But `PurchaseOrderForm.tsx:203-206` blocks submission with an error toast (*"Please select a vendor"*) for every PO **except** `purpose === 'manufacturing'` — directly contradicting the backend's "vendor is chosen later" design for the majority of POs (stock/project purpose).
- Once created, **vendor is rendered as read-only plain text** on the detail page (`PurchaseOrderDetail.tsx:1291`, `{label:'Vendor', value: po.vendor_name ?? '—'}`) — contrast with "Assigned receiver" right next to it, which is a live editable dropdown (`:1324-1353`). There is no equivalent control for vendor.
- The Edit Request mechanism (the general "propose a change, admin approves" path) explicitly excludes `vendor_id` and `currency_code` from what can be changed (`buildChanges()`/`initDraft()`, `PurchaseOrderDetail.tsx:4684-4738` — only `notes`, `expected_delivery_date`, line `description/qty/unit_price/uom`).
- The only place vendor gets set post-creation is buried inside `submitPOMarketPricing`, and even there it just silently re-sends the *existing* `po.vendor_id` (`PurchaseOrderDetail.tsx:2074`) — there's no actual vendor-picker input rendered in that section for the user to change it.
- Authorization gap found in the same area: `submitPOStorePricing` has an "organizer" fallback if no one holds the `store_pricing` position (`resolvers.ts:23809-23817`), but `submitPOMarketPricing` — the step where vendor gets attached — has **no such fallback** (`resolvers.ts:23879-23886`). A PO with no `procurement_officer` assigned in scope can get permanently stuck with no vendor and no way for anyone but an admin to unblock it.

**Decision:** fix outright — vendor should never be a hard requirement at creation.

**Recommended fix:**
1. Remove the frontend's vendor-required check for all purposes, not just manufacturing — this makes the form match the backend's already-intended design, no schema change needed. This is the one-line fix: delete/relax the `if (purpose !== 'manufacturing' && !form.vendor_id)` block at `PurchaseOrderForm.tsx:203-206` so vendor is never a hard blocker at creation, for any purpose.
2. Add a real, generically-available "Assign/Change Vendor" control on the detail page (same pattern as the existing "Assigned receiver" dropdown at `:1324-1353`), available from `draft` through `market_pricing`, gated by the same `procurement_officer` permission that already governs market pricing — rather than only being reachable as a side-effect of the market-pricing submit action.
3. Add the organizer fallback to `submitPOMarketPricing`/vendor assignment, mirroring the existing store-pricing fallback, so a PO can't get permanently stuck for lack of an assigned procurement officer.

**What could go wrong:**
- Once a vendor is changeable independent of the market-pricing step, you need a decision on what happens to line prices already entered under the old vendor's quote — likely just a "prices may need re-verification" warning rather than auto-clearing them.
- If vendor becomes freely editable later in the lifecycle (not just before market_pricing), that could let someone change the vendor on a PO that's already been through approval/pricing — recommend the editable window stays capped at `pending_approval` or earlier, matching the existing gate.

## Issue C — Receiving split across multiple people, per line

**Hypothesis:** This is mostly already supported — it's a UI-legibility problem, not a missing capability. Different people *can* receive different lines of the same PO today, each receipt event they submit is independently attributed to them, and partial receiving is the default behavior. What's missing is a single receipt form where each line names its own receiver in one submission.

**Evidence:**
- `po_receipts` (header, one `received_by`) → `po_receipt_lines` (many lines per receipt) is the schema (`007_procurement_schema.sql`). A PO's `receipts` field is an array (`graphql/procurement.ts:130-154`), and "Record Receipt" stays available across `approved`/`items_bought`/`goods_received` (`PurchaseOrderDetail.tsx:4377-4389`), so a second person can submit a second receipt for the remaining lines later.
- `ReceiptForm.tsx:65, 73-114` pre-fills each line's receivable quantity accounting for what's already been received, and a user can zero out any line they aren't the one delivering/receiving, sending only the lines with `qty_to_receive > 0` (`:236-241`).
- **The gap:** `received_by`/`received_by_name` is one field for the *entire* receipt submission (`ReceiptForm.tsx:57-64`, required at `:206-209`) — there's no per-line receiver field within a single submission. So two people receiving different lines of one delivery batch requires two separate "Record Receipt" trips, not one form with per-line attribution.
- Separately, `092_po_actual_price_and_receiver.sql`'s `assigned_receiver_id` and `056_po_receipt_receiver_photos.sql`'s `received_by`/`received_by_name` are three different "receiver" concepts across two tables — `assigned_receiver_id` is just a notification target/default suggestion, not an access-control gate (confirmed: `recordReceipt` only requires the general `procurement.po.edit` permission, `resolvers.ts:8018-8023` — anyone with that permission can receive any line, regardless of who's "assigned").

**Who receives, chosen at PO creation — already exists, just underused:** `PurchaseOrderForm.tsx:524-533` already has a "Received By" field at creation time, which sets `purchase_orders.assigned_receiver_id`. Today this is only a *default suggestion* — `ReceiptForm.tsx:101-111` auto-fills the receipt's `received_by` from it, but with a "change if someone else received" hint, and it carries no access-control weight. The recommendation below keeps that same shape — one named point of contact set at creation, freely overridable at receiving time — rather than trying to pre-decide the actual split at creation, since how a delivery actually gets split across people is normally only known once it happens.

**Decision:** default to a "Receive All" one-person flow, with per-line split as the explicit exception.

**Recommended fix:**
1. **Default state ("Receive All"), unchanged data model:** `ReceiptForm.tsx` already pre-fills every line's `qty_to_receive` to the full remaining amount and uses one `received_by` for the whole submission (`:57-64`, defaulted from `assigned_receiver_id`). Make this the explicit, named default: a "Receive All Items" toggle/checkbox at the top of the form, checked by default, showing one receiver field + all lines at their full remaining quantity — this is exactly today's form, just labeled so a user knows it's the one-person, one-trip path and not merely "the only option."
2. **Split path, only when unchecked:** unchecking "Receive All Items" reveals a receiver picker *per line* (defaulting each to the PO's `assigned_receiver_id`, overridable per line) instead of one form-wide receiver field. On submit, the form groups lines by chosen receiver and creates one `po_receipts` row per distinct receiver behind the scenes (each with its own `po_receipt_lines`) — this reuses the existing "multiple receipt events" data model but does it as one user action instead of requiring N separate trips through the form.
3. No schema change needed either way — this is UI-only, on top of `assigned_receiver_id` (already exists) and the existing multi-receipt-per-PO data model (already exists).

**What could go wrong:**
- Splitting one form submission into multiple `po_receipts` rows behind the scenes needs to keep the two mandatory photo categories (Vendor Receipt / Materials Received, `ReceiptForm.tsx:210-221`) sane per receiver-group — decide whether photos are required once per submission or once per receiver-group when split.
- If a line's chosen receiver in split mode isn't a real system user (e.g. a contractor/foreman), the same `received_by_name` free-text fallback from migration 056 should carry over per-group, not just for the whole-PO case.
- Low risk otherwise — this is additive UI work on top of an already-correct data model and an already-existing creation-time field.

## Issue D — "Actual price" entered too late (the core complaint)

**Hypothesis confirmed: this is a UI placement decision, not a backend or schema constraint.** The `actual_unit_price` write endpoints have zero status restrictions — they can already be called at any PO status. The only reason the price can't be entered earlier today is that no earlier screen renders the input field.

**Evidence:**
- `092_po_actual_price_and_receiver.sql` adds `po_lines.actual_unit_price` — nullable, no default, no status/stage relationship enforced at the DB level.
- All three write paths are status-agnostic:
  - `PATCH /:id/lines/:lineId/actual-price` (`orders.ts:2062-2109`) — no PO-status check.
  - `setPOLineActualPrice` GraphQL mutation (`resolvers.ts:17133-17162`) — no status check.
  - `recordReceipt`'s per-line `actual_unit_price` input (`resolvers.ts:8069-8079`) — already wired up on the backend.
- But the **only place the frontend renders an editable Actual Price input** is inside the `finance_audit` block of `PurchaseOrderDetail.tsx` (`:3010` onward, input at `:3339-3362`) — status 10 of 13 in the lifecycle (`lib/po-constants.ts:4-18`), after draft → pricing → verification → approval → issue → **buying → receiving** → *then* finance audit.
- The `items_bought` stage (where the price should live, per the decision below) currently only renders a bought/not-bought checkbox — no price field at all (`PurchaseOrderDetail.tsx:2758-2864`) — despite `assigned_buyer_user_id` and `is_bought` already existing per-line specifically for this stage (`198_po_items_bought.sql`).
- `VendorInvoiceForm.tsx` never reads or writes `actual_unit_price` at all — when a PO's lines are pulled into a vendor invoice, it copies the original `unit_price` (`mkLineFromPO`, `:116-124`), so today there are actually up to **four unlinked price entry points** per line (`unit_price`, `store_price`, `market_price`, `actual_unit_price`) with no reconciliation between the finance-audit number and whatever ends up on the vendor invoice.

**Decision:** move entry to the `items_bought` step, entered by the buyer.

**Recommended fix:**
1. Add the Actual Price input directly into the existing `items_bought` checklist UI, next to each line's bought/not-bought checkbox — call the existing `setPOLineActualPrice` mutation (already status-agnostic, no backend change required) at the point the buyer ticks a line as bought.
2. Turn Finance Audit's current "Actual Price" input into a **read-only review** of the value the buyer already entered, with the variance-vs-PO-price display kept as-is (`PurchaseOrderDetail.tsx:3238-3247`) — Finance's job becomes verifying/flagging a number that already exists, not being the first person to ever enter it.
3. Since `recordReceipt` also accepts `actual_unit_price` per line, decide whether to also allow entry there as a second capture point for cases where the buyer forgot — recommend making it read/pre-fill from whatever the buyer already entered at `items_bought`, rather than a second independent entry field, to avoid recreating the same "four unlinked prices" problem this fix is meant to solve.
4. Given `VendorInvoiceForm.tsx` currently ignores `actual_unit_price` entirely, worth a follow-up (separate from this fix) to have it default from `actual_unit_price` instead of `unit_price` when a PO line is pulled in, so the number the buyer entered actually flows through to AP instead of being re-typed a third time.

**What could go wrong:**
- Every PO currently auto-chains `approved → items_bought` in the same transaction (`packages/workflow/src/index.ts:270-278` — "no PO is ever observably left at approved"), and `items_bought` is explicitly documented as *"tracking only... deliberately does NOT transition the PO on its own"* (`resolvers.ts:24451-24459`). Adding a required-price rule at this stage needs to decide: does entering actual price become mandatory before a line can be marked bought, or optional like today's checkbox? Recommend optional-but-prompted, since making it mandatory could block the buyer from ticking a line bought before they have a final invoiced number in hand (e.g., price pending vendor confirmation).
- This only fixes the placement for the "every PO goes through items_bought" majority path. The dead/legacy `approved → goods_received` direct path (kept in code "for `recordReceipt`'s status check," per `resolvers.ts:24066-24070`) means a small edge case could theoretically skip the buying screen entirely — worth confirming with engineering whether that path is truly unreachable in practice before relying on `items_bought` as the only actual-price entry point.

## Issue E — The structural risk underneath all four (biggest lever, not one of the original complaints)

**Finding:** There are **two independent, non-proxying implementations of the entire PO workflow** — a REST microservice (`services/procurement/src/routes/orders.ts`, 2109 lines + `receipts.ts`) and the GraphQL gateway (`services/gateway/src/graphql/resolvers.ts`, PO logic spread across ~2,800 of its 27,386 lines). **The web app only talks to the GraphQL gateway** — the REST microservice is a largely dead parallel path that nonetheless keeps getting maintained (or not) independently.

**Evidence it has already caused real drift, not just theoretical risk:**
- `receipts.ts`'s status gate (`:78-87`) still checks `status IN ('approved','goods_received')` — missing `'items_bought'`, which migration 198 introduced. The GraphQL version was fixed (`resolvers.ts:8039`, with a comment explaining why); the REST version was not. A receipt can't currently be recorded through the REST path for any PO that's gone through the buying checklist.
- `verified_price`/`verified_price_currency` (added in migration 047) are populated by the GraphQL price-verification mutation but never touched by the REST equivalent — so whether those columns are populated depends on which implementation handled a given PO.
- `actual_unit_price` recomputes `total_price` in the REST PATCH endpoint but does **not** in the GraphQL `recordReceipt` path — the same field, updated two different ways with two different side effects depending on which mutation was used.
- Stock costing basis differs: REST explicitly uses `actual_unit_price` (falling back to `unit_price`) for inventory cost basis with a comment saying why; GraphQL's `recordReceipt` writes stock-move cost from `unit_price` even when an `actual_unit_price` was just recorded in the same call.
- The web app additionally still exports dead GraphQL mutations (`submitPO`, `approveL1PO`, `approveL2PO`, `rejectPO`, `markOrderedPO`, `apps/web/src/graphql/procurement.ts`) built for a status model migration 030 replaced — these can no longer succeed against the current status CHECK constraint, but nothing removed them.

**Decision: keep GraphQL (`services/gateway`), remove the REST `services/procurement` microservice.** Verified directly, not assumed:
- `services/gateway/src/app.ts:198` proxies `/api/v1/procurement` → `PROCUREMENT_SERVICE_URL`, but a repo-wide grep for that proxy path, for `PROCUREMENT_SERVICE_URL`, and for any axios/fetch call into `/procurement/...` found **zero callers** — not in `apps/web`, not in `apps/mobile` (which has no procurement/PO references at all), not in any script.
- `services/procurement/src/app.ts:1-40` shows the entire service is PO-adjacent: `vendorsRouter`, `ordersRouter`, `receiptsRouter`, `poAttachmentsRouter`/`poReceiptAttachmentsRouter`/`vendorAttachmentsRouter`, `returnsRouter` — nothing else lives in this service that would need to keep running for an unrelated reason.
- The GraphQL side is also demonstrably the one actually being kept current — it's the one with the `items_bought` status-gate fix, the `verified_price` population, and the organizer fallback on store pricing that GraphQL has and REST doesn't. Maintaining two copies has already produced real bugs; consolidating onto the one that's actually maintained is the safer direction rather than trying to revive the REST copy.

**Recommended action:** delete `services/procurement` entirely (`routes/orders.ts`, `receipts.ts`, `returns.ts`, `vendors.ts`, `attachments.ts`, `lib/po-helpers.ts`, `lib/po-authorization.ts`, its tests, its `app.ts`/`index.ts`), remove the `/api/v1/procurement` proxy route and `PROCUREMENT_SERVICE_URL` from `packages/config/src/env.ts`, and remove the service from `ecosystem.config.cjs`/`docker-compose.yml` if it's still listed as a running process there.

**What could go wrong:**
- This is a delete of an entire running service — before actually removing it, do one more pass beyond the grep already done here: check `ecosystem.config.cjs` and `docker-compose.yml` for whether it's actively deployed (if it's running in production right now, confirm nothing external — a Postman collection, a partner integration, a cron script outside this repo — points at it before taking it down), and check `packages/workflow` isn't imported *only* by the REST side (both `orders.ts` and `resolvers.ts` call into it — confirm gateway's copy doesn't secretly depend on something that lives in `services/procurement` before deleting).
- Once deleted, every future PO fix in this document (Issues A–D) only needs to be made once, in `services/gateway/src/graphql/resolvers.ts` — which also means resolvers.ts (already 27,386 lines) keeps growing as the single home for PO logic. Worth a separate, later note to Finance/engineering that resolvers.ts itself may deserve splitting into per-domain files at some point — not urgent, but flagged here since removing the REST alternative makes this file even more central.

**Why this matters for Issues A–D specifically:** every fix above (consolidating currency columns, adding a vendor-edit control, changing where actual price is entered) needs to be made correctly in whichever implementation(s) are actually live, and any fix made in only one place risks silently not applying to POs routed the other way — exactly the pattern that already produced the `items_bought` receiving bug. Resolving Issue E first makes every other fix in this document lower-risk to implement correctly.

## Other findings worth flagging (lower priority, cheap cleanup)

- **Dead legacy mutations**: `submitPO`/`approveL1PO`/`approveL2PO`/`rejectPO`/`markOrderedPO` in both `resolvers.ts:7908-7999` and `apps/web/src/graphql/procurement.ts` reference a status model that no longer exists (migration 030 replaced it). Safe to delete — nothing can call them successfully today.
- **`po_lines.account_id`** sat unused for ~190 migrations before finally being wired up in `197_advance_automation.sql` — a sign of schema entropy worth a periodic "is this column actually used" audit rather than a one-off fix.
- **Two full lifecycle redesigns** (migration 030, then 094) plus a partial third (198's `items_bought`) have left dead/near-dead statuses and transitions "for safety" — e.g. the `approved` status is now instantaneous for every PO (auto-chains to `items_bought`), and its direct `→ goods_received` transition is kept only because `receipts.ts` still checks for it. Worth a dedicated cleanup pass once Issue E is resolved, since collapsing dead states safely requires knowing which implementation is canonical first.
- **`store_pricing` is explicitly a "skip me" stage** in the current UI copy (*"Skip entering prices — store prices will be filled in automatically"*, `PurchaseOrderDetail.tsx:1806-1827`) and Emergency-priority POs already bypass inventory-check/store-pricing/market-pricing entirely — both signals suggest the 13-status pipeline is longer than real usage patterns want, and there may be room to formally shorten it once the other fixes above settle.

## Follow-up: bugs found by live browser testing (chrome-devtools MCP)

A real click-through test session (via the chrome-devtools MCP browser integration) surfaced 4 bugs, 3 of them real regressions from this session's own changes. All fixed and verified (`tsc --noEmit` clean, key ones checked against the live dev DB) except Bug 3's returns workflow, whose true scope turned out much larger than first reported — see below.

- **Bug 1 (critical, blocked all PO creation) — FIXED.** `createPurchaseOrder` (item 7's currency work) and the `GET /admin/po-fx-rates` route both queried `companies.default_currency` — a column that doesn't exist; `companies` only has `currency_code`. The real field lives on `system_configuration` (one row per company), which turned out to have **two** candidate columns: `default_currency` (general company default) and `default_po_currency` (specifically for POs). Confirmed `default_po_currency` is correct — it's the one already read/written by the company-settings admin UI (`services/auth/src/routes/company-management.ts`) specifically for this purpose, distinct from the general default. Fixed both call sites to `SELECT default_po_currency FROM system_configuration WHERE company_id=$1`, matching the existing join pattern used elsewhere in the file. Verified: the corrected query runs successfully against the dev DB for all 3 existing companies (all currently `IQD`); also corrected the migration comment that had the same wrong claim.
- **Bug 2 (crashed receiving when location left blank) — FIXED.** `recordReceipt` passed the optional `location_id` straight into `stock_moves.to_location_id`, which is `NOT NULL` — leaving the "Receiving Location (optional)" field blank (exactly what the UI invites) crashed the whole receipt. Added the same default-warehouse-then-any-active-location fallback already used elsewhere in this file (`issueStockForPOLines`), with a clear error only if a company has zero active stock locations at all. Verified against the dev DB: the test company actually has no `type='warehouse'` location, only a `site` one — confirming the two-tier fallback is genuinely needed, not just theoretical, and that it correctly cascades to the second tier.
- **Bug 3 (dead REST calls after the procurement service was deleted) — approval-queue badge FIXED, line comments FIXED, returns workflow NOT YET DONE (see below).** Three real gaps in item 5's "zero callers" verification — a miss on my part, worth being direct about:
  - `useApprovalQueueCount.ts` (sidebar badge, polled every 60s) — rewritten to use the existing `myApprovalQueue` GraphQL query (Apollo `useQuery` with `pollInterval`) instead of the dead REST count endpoint.
